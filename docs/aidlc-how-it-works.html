How it works AI-DLC · ss-trigent/aidlc / 3 August 2026

Seven AI juniors. Three gates. Humans hold every key.

A customer need goes in one end and provably-working software comes out the other. At each of three boundaries a named human clicks Approve in GitHub — and everything a machine can check is checked by one CI status that fails the build. Nobody on the team needs to read a framework file, know an ID, or touch git.

01The flow

The whole lifecycle, end to end

The source methodology has ten sequential phases. Every one survives — but they are grouped into three enforced boundaries, because a gate is a mechanically checked, human-approved merge, where a phase was a heading someone typed.

Starts here A customer need, in their own words — saved verbatim, so every requirement has a source

Gate 1 · Inception

Discovery

Are we building the right thing?

Who drafts
/ba/ux/architect advises/manager plans
What comes out
Three ordered pull requests: a requirements doc with numbered, testable requirements → a screen spec per screen, every state numbered, plus design tokens → user stories with numbered acceptance criteria. Alongside: an advisory DB + app architecture, and an advisory delivery plan
The distinctive step
A grill pass — ambiguities interrogated one question at a time before anything is drafted. What survives unresolved becomes an open question with a named owner, never a guess dressed as a requirement.

Human approves Three reviews, in order: the product owner merges requirements, the designer approves screen structure and the product team the styling, then the product owner merges the stories. Each merge commit is that step's scope baseline.

Gate 2 · Construction

Delivery

Does this story provably work?

Who drafts
/dev/qa/architect
What comes out
A spec package for the story — technical requirements traced to its criteria, an implementation plan, impact analysis, decisions, traceability — then one pull request holding everything: code, tests named after the criteria they prove, a decision record if a real trade-off existed, and the updated traceability links
The distinctive step
The plan is reviewed before the code exists. The developer writes the implementation plan and impact analysis first, and a human approves them in chat — the cheapest moment to catch a wrong assumption. Then test first, from the requirement: QA derives tests from the story before reading the code, so a passing test has failed at least once.

Human approves — twice D1: the written implementation plan, in chat. The developer stamps the approver, the date, and the SHA of the plan as read into the plan file, so a later edit is detectable. D2: the story PR — a human reviews and merges, every required check green first. Merged means delivered. Nothing else between them needs a human.

Gate 3 · Operations

Release

Is production safe?

Who drafts
/devops/manager reports
What comes out
The pipeline itself, releases, a current rollback procedure, monitoring tied to the performance budgets the requirements set
The distinctive step
Promotion only through the pipeline. A step someone has to do by hand is a pipeline bug, filed as an issue. A red quality step is never switched off to unblock a release.

Human approves A human approves each promotion in the pipeline — dev, then QA, then production. Authenticated, per environment.

Inside Gate 1 — scope locks left to right

Discovery runs as three ordered pull requests, stories last (ADR-003), so a story is never written against scope that is still moving. Design itself runs in two passes (ADR-004): structure — the screen spec, approved by the designer — then styling — tokens and rendered previews, approved by the product team. Hi-fi frames stay in the design tool. The order is charter-enforced, not CI-blocked: the personas refuse to run ahead, and the human review holds the line — a deliberate choice over a new gate check.

1

Requirements freeze

/ba grills, then drafts the requirements doc. The product owner merges — and the requirements can no longer move.

2

Design approved

/ux drafts each screen from the requirement it serves. The designer signs off the structure; the product team signs off the styling. A styling change that forces a structural change reopens the structure pass.

3

Stories sliced

Only now /ba slices stories, citing frozen requirements and already-approved screens. This merge is the locked scope Gate 2 builds against.

∥

Advisory, in parallel

Once requirements freeze: /architect drafts the DB + app architecture (its own PR, blocks nothing) and /manager proposes a delivery plan — estimates and two-week sprints the human locks in Jira. Neither gates anything.

Ends here Production — and then feeds straight back:

The loop. An incident, a defect, or a change of mind does not get its own bureaucracy. It becomes a GitHub issue — bug or change-request — which either reopens Gate 1 for the affected artifacts or lands as a fix PR that must add a regression test. Postmortem lessons are recorded as edges in the traceability graph. Nothing is learned off the record.

02The people

Seven personas, seven real counterparts

One persona per human who can actually approve its work — a persona with nobody to report to produces output nobody owns. You type your command; it interviews you and prepares the paperwork. You never write a prompt.

/aidlc

Anyone · start here

The front door. Works out who you are and what you need, then becomes the right persona.

You“I'm new — what is this project?”
GetA briefing, then it continues as your persona. No second command.

/ba

Business analyst · product owner

Turns a need into requirements and stories. Owns what the product must do.

You“Planners need to compare shipping routes by cost and time.”
GetA requirements PR first; stories come later, once design is approved — one link to review each time.

/ux

Designer

Turns approved requirements into screen specs — structure first, then styling — and the design system. Owns what the user sees and does.

You“Design the results screen.”
GetEvery state numbered, plus a token file you import into Figma or Penpot.

/architect

Solution architect · tech lead

Drafts the DB + app architecture once requirements freeze, advises where trade-offs are real, and reviews every story PR. Advisory only — cannot edit the repository; a reviewed PR lands what it drafts.

You“Review this pull request.”
GetRated findings and a suggested verdict. Your review is the authority.

/dev

Developer

Implements one approved story as one PR: code, tests, and real evidence pasted in.

You“Build the next ready story.”
GetA branch, a failing test first, then the code that turns it green.

/qa

QA engineer

Derives tests from the requirement before reading the code, and files reproducible defects. For browser-level work it writes a step-by-step plan you approve before any test exists, then generates Playwright tests against the running app.

You“This screen shows the wrong total.”
GetA defect issue with steps and real output — and the fix needs a regression test.

/devops

DevOps engineer

Owns the path from merge to production: pipelines, promotions, rollback.

You“Why is the build red?”
GetThe failing step, the cause, and a fix that rides a normal PR.

/manager

Delivery manager

Reports, routes, and proposes the delivery plan — estimates and sprints the human locks in Jira. Reads status from GitHub only. Holds no gate authority and cannot edit the repository.

You“Where are we? What's stuck?”
GetStatus derived from pull requests, issues and checks — never from a document.

Two personas are read-only by tooling

The framework has always said the architect's review is advisory and the manager holds no gate authority. Those were words. Both now declare the write tools as disallowed — they cannot change a file — and the validator fails the build if that restriction is ever removed.

Each persona exists three times

A charter (the contract), a command you type, and a delegatable agent for parallel work. The validator proves all three agree, so a persona cannot quietly drift from its contract.

The one limit that is not tool-enforced

No persona may merge, approve or close anything. A shell is a shell, so this is a charter rule ranked above any instruction — and the framework says so plainly rather than implying CI catches it.

03Using it

One relay, hand-off by hand-off

Each stage is owned by one human typing one command. The persona interviews you, prepares a pull request, and your merge passes the baton — it always ends by telling you who runs next and what they type.

/ba
Gate 1 · requirements The BA / product owner types /ba and talks through the customer need in their own words — pasting meeting notes is fine. The persona grills every ambiguity first, drafts the requirements doc, and opens the PR. Your merge freezes the requirements and hands off to the designer.
/ux
Gate 1 · design — structure The designer types /ux. One screen spec per requirement that needs UI, every state numbered ST-##, conflicts listed until resolved. The designer approves the structure.
/ux
Gate 1 · design — styling Same persona, second pass: design tokens for both themes and previews that render every state styled. The designer takes the exported tokens into Figma or Penpot for hi-fi frames (frames stay in the tool). The product team approves the styling. Cycle: a styling change that forces a structural change reopens the structure pass.
/ba
Gate 1 · stories The BA returns. Only now — with requirements and screens frozen — are stories sliced, each citing its requirements, its screen, and numbered acceptance criteria. The product owner's merge locks the scope — Gate 1 is done.
∥ advisory
In parallel, once requirements freeze /architect drafts the DB + app architecture — its own PR, blocks nothing. /manager proposes the delivery plan — estimates and two-week sprints you lock in Jira. Neither gates the relay.
/dev
Gate 2 · one story, one PR The developer types /dev and names a ready story (or asks for the next one). A feat/US-### branch, then the spec package written before any code — and the plan inside it is what a human approves to unblock the work. After that: a failing test per criterion first, then the code that turns it green — evidence pasted into the PR.
/qa
Gate 2 · same PR The QA engineer types /qa. Tests are derived from the story before reading the diff — positive per criterion, then negative, then boundary. Anything that can never be automated — a real email arriving, a device, a visual judgement — becomes a written manual case in the spec package instead; most stories have none. Wrong behavior found any time later becomes a bug issue whose fix PR must add a regression test.
/architect
Gate 2 · review, then merge Anyone asks /architect to review the PR: rated findings, a suggested verdict, advisory. A human merges when every check is green — merged means delivered. Cycle: repeat /dev → /qa → review for every story in the locked scope.
/devops
Gate 3 · release The DevOps engineer types /devops for pipeline work. Promotion runs dev → QA → production, and you approve each step in the pipeline — never out of band.

The cycles. A defect → bug issue → fix/#N PR with a regression test. A change of mind about approved scope → change-request issue → the relay re-runs from the affected Gate 1 step (requirements, design, or stories) — same PRs, same reviews. Production lessons land as lessons edges in the traceability graph. /manager tells you where the baton is at any moment; /aidlc is the front door when you don't know which command is yours.

Persona or agent — two ways to run the same role

You are doing your own stage

Type the command

  • /ba, /ux, /dev, /qa, /devops, /architect, /manager Conversational: it interviews you one question at a time, in plain language, and prepares the paperwork. You never touch git or file paths.
  • /aidlc When unsure — it works out who you are and becomes the right persona.
  • Any editor The same commands exist in Cursor, opencode and Copilot Chat — generated from the same charters, and CI fails if they drift (ADR-005).

Work runs alongside you

Delegate the agent

  • aidlc-ba · aidlc-ux · aidlc-dev · aidlc-qa · aidlc-devops · aidlc-architect · aidlc-manager The same persona as a delegatable subagent — for parallel or background work: two stories under two aidlc-dev agents, a coverage check handed to aidlc-qa mid-session, an independent PR review from aidlc-architect.
  • One contract, proven The charter in ai/roles/ binds both surfaces; CI fails if they drift apart — and the advisory agents (aidlc-architect, aidlc-manager) cannot write files at all.

Either way: no persona may merge, approve or close — that is always you, in GitHub

The rhythm at every hand-off

1

You talk

Type your command and describe what you have in your own words. Paste meeting notes if that is easier. One question comes back at a time, in plain language, with a sensible default offered.

2

It gets grilled

Vague answers get pushed on before anything is written: “what happens when…?” for every edge. Anything still unresolved is recorded as an open question with your name on it — not quietly invented.

3

You get a walkthrough

Not a file dump. Each item in one sentence, what was decided on your behalf, and what is still your call. A repository is not a readable format for an approver — the conversation is.

4

You click Approve

One GitHub link. Two clicks. That authenticates who approved exactly what, bound to an exact commit. Then it tells you who is up next and what they type.

Approval is a GitHub review — never text in a document, never a message in a chat.

This is the load-bearing decision of the whole framework. A document header saying “Approved by: Priya” can be typed by anyone and edited later. A pull-request review binds a verified identity to a specific commit, permanently. The first implementation of this methodology used document headers, and an independent review called it what it was: compliance theatre.

04Worked example

One real story, all the way through

Not an illustration — these are the actual artifacts in the repository today, with their real identifiers. Solid rungs are built and machine-checked; dashed ones are the honest state of a project that has not started building yet.

REQ-003
Gate 1 · the requirement “Each returned route lists its legs: mode, from and to, scheduled departure and arrival, cost, duration, total transfers.” Testable and sourced — traced to the project charter, not to someone's memory.
US-003
Gate 1 · the story “View ranked route results.” Cites REQ-003 and the usability requirement NFR-003. The link is bidirectional and validated — a requirement cannot point at a story that does not point back.
AC-01…04
Gate 1 · the criteria Four numbered criteria in Given/When/Then form. The manifest's list must match the headings in the story file exactly, so a criterion cannot be silently dropped.
SCR-002
Gate 1 · the screen The ranked-results screen: purpose, layout, accessibility, and the structural decisions with their rationale. Two unresolved conflicts block its sign-off — including that the objective score is a raw 0–1 number the requirements never define.
ST-01…06
Gate 1 · the states Ranked list, expanded legs, loading, no-route, error, single-leg. Numbered exactly like acceptance criteria, for the same reason: an unnumbered state is one nobody notices is missing.
route-card
Gate 1 · the component Real HTML on real tokens, rendering all six states, opening in a browser with no build step. CI proves every state is actually rendered — not merely listed.
Tests
Gate 2 · not started Each criterion needs a test whose name cites US-003/AC-##. The moment this story moves to its delivery branch, having no tests stops being a warning and fails the build.
Code
Gate 2 · not started The Angular feature. There is no code edge in the graph yet — the most consequential gap in the system, and the cheapest to close: record the story PR's merge commit.
Deployed
Gate 3 · waiting on an environment No deployment edge and no monitoring edge. Declared scope in the release gate rather than pretended practice.

Why the chain matters

Ask “why does this line of code exist?” and the answer is a path back to a sentence a customer said. Ask “what breaks if we drop this requirement?” and the graph lists the stories, screens, states, components and tests that hang off it — before anyone edits anything.

05Enforcement

One command decides if any of this is real

The operating principle is blunt: a rule that is not checked by CI or by a GitHub setting is guidance, not governance. Sixteen checks run on every pull request as a single required status.

1

Every identifier is unique across the whole repository — no two documents claiming the same number

2

Every link resolves in both directions, and every requirement a story cites is a node in the graph — nothing hangs off one-way

3

The criteria list matches the story file exactly — a criterion cannot vanish between document and graph

4

Every criterion is named in a passing, active test. A story in delivery with no tests fails outright, and a story the traceability graph has never heard of fails too — otherwise it would slip past this rule instead of being caught by it — citations in comments or skipped tests are not proof

5

Test files that cite a story are listed against it — no stale graph under-reporting coverage

6

Every product project can actually run tests — untestable code is a build failure, not an oversight

7

The published traceability matrix matches what the graph generates — no hand-edited view that flatters reality

8

Decision and lesson links point at real artifacts — no dangling references

9

The distributable copy of the framework matches its source — other teams cannot install a drifted version

10

Every persona's three surfaces agree, and the two advisory personas still cannot write — authority is structural, not aspirational

11

Design is complete: a story with UI cites a screen, a screen traces to a story or the requirement it serves, every numbered state is rendered by a component, and the exported token file matches the stylesheet — eight sub-rules

12

Ticket templates are safe: none declares a field that would forward approval or duplicate what the tracker owns, no unknown placeholders, no stale markup — see section 07

13

The Cursor, opencode and Copilot persona surfaces match their sources — generated files, never hand-edited — ADR-005

14

The framework itself cannot be quietly edited. Every framework-owned file matches a shipped hash lock; an adopting team edits only its own standards, ticket templates and project context — a different rule goes upstream as a change request

15

Browser-test evidence from another repository is checked, or absent. A QA team that keeps its end-to-end tests in their own repo publishes an evidence file; the validator checks every criterion it claims really exists and that every pass carries the run it came from. No file means no requirement — a team whose tests live in this repo is untouched by the rule — the end-to-end layer · ADR-006

16

A development spec package, if one exists, tells the truth. Every technical requirement in the spec has a row in the traceability table, every file that table points at exists, every story and criterion it names is real, it is listed in the spec index, and the plan's approval records who approved it, when, and which version — so a plan edited after approval fails unless the change is logged. A story with no package fails nothing: the validator cannot know how big the task was — newest addition, the development spec packages · ADR-007

What it deliberately cannot prove

That a test's assertions are meaningful, or that a screen state is handled well. An empty test body with the right name satisfies the tooling. Judging quality is the reviewer's job — which is exactly why every gate still ends at a human.

And the one gap that undermines all of it Open

Branch protection is unavailable on this repository's plan. Every check above is visible red or green on each pull request, but nothing blocks a merge. It is an administrative setting, not code, and it is the highest-value outstanding item in the whole system.

The identifier scheme, in full

REQ-###A functional requirement
NFR-###Speed, usability, reliability
RISK-###A recorded risk
US-###A user story
AC-##An acceptance criterion, scoped to its story
SCR-###A screen specification
ST-##A screen state, scoped to its screen
ADR-###A decision with a real trade-off

Defects and change requests are GitHub issue numbers, not documents. Test cases are test names, not records. Personas explain each identifier the first time you see it and never ask you to remember one.

06Design

Design is a handoff, not a tool we own

The newest change, and the one that most affects how a designer joins. The repository sits upstream of whichever tool the designer already uses. It holds what a gate can check; the tool holds what a gate cannot.

Canonical · CI-enforced · in the pull request

The repository

  • Screen specsPurpose, layout, every numbered state, accessibility, decisions with rationale, and conflicts that block sign-off.
  • Design tokensOne canonical stylesheet, plus a generated export in the W3C standard format.
  • Component previewsReal HTML on real tokens, every state marked. No build step, no network.

Figma · Penpot · Sketch · paper

The designer's tool

  • The imported token setTokens Studio, Penpot tokens, Style Dictionary — anything reading the standard.
  • Wireframes and hi-fi framesOne frame per numbered state; the numbering is the checklist. Frames are not checked in.
  • Exploration and critiqueVariants, comment threads, annotation — where designers already work well.

One way only

Nothing is authored downstream and pulled back — that would put a Gate 1 artifact outside version control. The token export is generated from the stylesheet and CI fails if the two disagree, so the palette a designer draws with cannot drift from the palette that ships. That is a guarantee a design-tool-first workflow could not give, and it is the whole argument for pointing the arrow this way.

Why /ux became its own persona

Design used to be a sketch pasted into a story, and one persona covered both crafts. Once design became CI-enforced, that persona was producing artifacts no one with design authority reviewed. Enforcing an artifact reveals whether its role has an owner.

The honest limitation

This does not capture a design tool's collaboration surface — comment threads, handoff annotation, visual history. The collaboration a gate depends on (which states exist, which conflicts are open, who owns them) is now in reviewable files. The rest stays in the tool.

07Tracking

A board for everyone without repository access

Clients, some managers, and testers need to follow this work and will never open a pull request. Jira is the board they already read. It carries delivery tracking, a client-readable view, and test evidence — and no approval whatsoever.

Approval never travels — in either direction.

A ticket moved to Done, a sign-off field, a comment saying “approved” — none of these open or close a gate. A pull-request review authenticates who approved exactly which bytes; a ticket field authenticates nothing once it has crossed an integration boundary, and what was approved is no longer recoverable. That is the one thing this framework will not forward through an integration.

Who does what with it

/ba — on request

Creates the epic, story and change-request tickets when the human asks. A story that is not yet approved says Draft — awaiting approval, so the board never implies agreement that does not exist.

/qa — bugs and test evidence

One test ticket per acceptance criterion, its result filled from a real pipeline run. A criterion with no automated test reads Not yet automated — never a pass nobody earned.

/manager — keeps it current

Mirrors delivery status from GitHub and cross-links tickets to their specifications. Reporting outward is inside its charter; it still holds no gate authority in either system.

/architect — never writes

Its read-only guarantee is a tool restriction on files, which does not reach an external system. So this one is a charter rule, not tool-enforced — stated plainly rather than pretended.

Five templates, filled from the specification

TicketBuilt fromCarries
EpicAn epic artifactGoal, its stories, open decisions
StoryA user storyWhat it delivers, the requirements behind it, every acceptance criterion, its screens, what is still undecided
TestOne acceptance criterionWhat is being proven, the result, and the pipeline run it came from

Each ticket deep-links its specification, so the board is never where someone reads the spec — only where they see the state of it. Sprints, assignees and estimates stay the tracker's business; mirroring those into the repository would recreate the status-file habit this framework was rebuilt to remove.

Kept honest by construction

One writer, dry run by default

Every write goes through a single tool that prints the exact text a client will read and changes nothing. So client-facing wording is reviewed in a pull request before it reaches a live board. No credentials needed to do that.

A refusal list in code

Status transitions, sign-off fields, sprint, assignee, estimate and worklog are refused regardless of what a template or an instruction asks for. Check 12 rejects a template that even declares one.

Losing the tracker cannot break the build

A recorded ticket number is a convenience for humans, not a governance edge. A missing one is a warning. That is the test of whether an integration stayed in its lane.
